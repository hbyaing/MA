# 第11项：冻结留出验证、职业认证与炉体渲染修复

本项接入已批准的丹道研析台V2认证页，不新增职业账户，不改变反应核心、旧丹药或已有药效规则。生产网络协议104；Minecraft1.20.1 / Forge47.4.10 / Java17构建。PCL安装目标仍为用户指定的Forge47.4.26实例。

## 玩家流程

1. 完成既有配伍、火候和公开研究法前置，在反推页保存本人候选版本。
2. 认证页的每个版本有五张卡：本人反推、恢复基础、回灵基础、清净基础、职业晋阶。上下页切换；悬停正文查看所选版本、实际投料和冻结规则。
3. 在生存模式冻结方案，固定规则上下文、材料/药龄/用量/设备/火种/工序范围、公开药效目标、最低品级、置信方法与样本数。允许开炉时刻、炉内预储灵力及真实天象变化；它们是验证扰动，不是自动稳定奖励。
4. 冻结后该角色接下来规定数量的V5批次自动绑定，包含普通炉自由/固定丹方与天地为炉。不能换炉挑选结果，失败、事故、中止、非目标投料或创造模式炼制均占样本位置。旧的活动批次不追溯计入。没有自动代炼入口。
5. 完成全部样本后提交，保留成功/失败/待完成、成丹率、目标药效率、目标品级率、事故率、药效强度/时长范围和置信下界。失败协议保留，复制或改名相同内容不能重置它；真实改变后的新方案必须重新冻结并采集新样本。

默认策略 `data/wuxingxiantu/alchemy/certification.json`：30个批次、95% Wilson下界至少0.80、至少2个新原料批次及2种**成功样本**天象组合。24/30和28/30均不通过，29/30和30/30满足置信门槛，但还必须满足独立性、完整性及覆盖要求。可配置30–64批、更严格置信/下界与覆盖；不接受放宽到设计基线以下的配置。策略在冻结时复制，之后资源重载不回改既有验证结果。

## 独立性与材料来源

- 冻结前审计该作者全部服务器批次，而非前128条展示索引，排除发现/调参使用过的种子与药材批次。审计有8192个服务器批次文件预算；超过预算停止新的冻结并报诊断，不默默跳过历史。展示索引上限仍为128，不限制留出账本收集。
- 正式新批次种子仅保存在服务器，客户端只见授权摘要。重复种子失败；每个留出批次中的药材也必须尚未用于历史或先前留出批次。跨多个药材来源的投料要求每个来源均独立，不能掺一件新材料来洗旧材料。
- 药材新收获和创造模板首次初始化时记录`WuxingHerbLot`。拆分和炮制保留来源；直接调整年份不会凭空产生新批次。旧药材保持原有数量/年份/其它NBT、照常炼制，但无可证明来源的旧库存不能充当独立留出材料。
- 储物袋仍按物种/炮制等合并条目、保存精确年份；条目内部同时保存年份→来源批次→数量。取出一次只来自一个真实来源，存取及保存重载不混批、不生成新UUID；旧袋子的年份数组继续读取，不对旧库存补造来源。
- 本人反推认证另需该版本源自本人自由炼制，且有涉及该源批次的真实单因素对照。仅抄固定丹方、引用别人的样本目标或无关对照不构成本人独立论证。

## 持久化与恢复

`data/alchemy-v5/certification/<owner>.nbt`是既有批次权威日志的认证凭证扩展，保存冻结协议、自动顺序预留、种子指纹、来源首次使用序号、全部结果和正式品阶；不是第二个职业账户。每次更新通过同一有界NBT和强制落盘/原子替换实现，成功提交后才发布内存缓存。32个协议与1MiB账本预算在冻结时预检，为未来结果保留空间。

先持久化验证位置，再提交实体炉扣料日志；天地为炉只在付款提交边界绑定。中断于两文件之间时，保留预留位置；完成采集后仍不存在的物理提交按失败处理，不能用后来成功替换。已存在且仍活动的任务保持待完成，不能强制当作丢失任务关闭。物理批次已提交而认证尚未结算时，提交认证会重读权威终态并补记；离线结算也通过这条路径恢复。发证前重新检查全部物理终态、所有者、协议绑定、冻结药效摘要与V5有效性。

职业称号继续使用`PlayerCrafts.alchemy`，正式品阶镜像为`AlchemyCertifiedRank`。凭证先提交，再更新职业记录；旧职业保存晚于凭证时，读取正式品阶会修复镜像。旧Rank、心得和代表作保留，不自动折算成新正式认证，也不再直接替代认证晋阶。一至三品要求恢复基础；四至六品另需回灵基础；七至九品另需清净基础与本人反推。每类验证都要求对应目标品级，晋阶还检查既有境界、知识及当前规则/策略。高品凭证不能绕过基础集合；研究节点不被改写成“整个声明域已认证”。

本项不宣称任意文件损坏、人工篡改整个服务器目录或整世界回滚具有不可回滚认证。更换规则/认证策略保留旧证据，但旧凭证不能直接晋升当前新标准；新标准进入冻结身份，允许另开严格的新协议而不继承旧样本；完整多人/旧档迁移/故障组合继续归第12–13项。

## 报告中的炉体崩溃

用户2026-10-29报告的链路是原版草方块AO取相邻炉体形状时，`AlchemyFurnaceCollision`经有界`RenderChunkRegion`再次读取远端炉心，导致区块数组越界。修复为每个部件保存并同步炉心朝向，仅查本地部件数据和预计算形状。旧部件未同步朝向时使用四朝向形状的保守并集；服务器在炉心已加载后补齐，渲染线程不访问远端炉心或实时ClientLevel。碰撞与选择框均走此路径。没有删除草方块、关闭AO或更改用户存档结构。
